Agri Telemetry & Forecasting Platform

23/09/2026 // Master Engineering Research & Execution Document // Status: UNKNOWN / INITIALIZING
Core Principle

Build the evidence before building the complexity.

PLAN → RESEARCH → SPECIFY → BUILD → TEST → MEASURE → REVIEW → UPDATE

Architecture must be justified by requirements and empirical evidence, not by the desire to use impressive technologies. Candidates like MQTT, Redis Streams, MLflow, Docker, and specific forecasting models are considerations, not commitments. Research determines the final stack.

Engineering Discipline Rules
  • No fabricated data: Do not invent research findings, metrics, datasets, test results or scientific conclusions.
  • Strict Vocabulary: Use the status badges (HYPOTHESIS, RESEARCHING, DECIDED, VALIDATED) honestly. Do not mark anything VALIDATED without documented evidence.
  • Evidence-driven architecture: Do not lock architecture before validating requirements. Traceability is mandatory.
  • No architecture theater: Do not add technology simply because it looks impressive. Prefer the simplest architecture that demonstrates the required capability.

The Central Operational Question

"Can continuously arriving field telemetry be used to establish a reliable temporal baseline for soil-moisture conditions and detect meaningful deviations early enough to support an operational decision?"

01 Project Brief

Working Hypothesis Historical satellite analysis identifies stress reactively. Operational systems need to continuously ingest new observations and compare them against expected conditions to alert managers before crop failure.
Target User UNKNOWN [e.g., Farm Managers, Agricultural Insurers, Agronomists.]
Why Telemetry Matters Provides high-frequency, localized ground-truth data that complements low-frequency, macro satellite observations.
Why Forecasting Matters Anomalies can only be detected if we have a mathematically sound expectation of what "normal" should be for the next N days.
Useful Output HYPOTHESIS An automated alert payload logging the sensor ID, current reading, forecasted baseline bounds, and a persistence severity score.
Portfolio Differentiation Crop Stress Intelligence = Remote Sensing / Geospatial screening (Spatial context).
This Project = Event-Driven MLOps / IoT / Time-Series (Temporal context).
Explicitly Out of Scope DECIDED Physical hardware deployment, proprietary inaccessible farm APIs, UI dashboards (until the API is fully proven).

07 Build Strategy

Implementation executes in vertical slices to prove scientific and data value early, avoiding technology-first dead ends. The sequence may change after research.

  1. Slice 1 (Data & Forecast): Fetch historical data, establish baseline model, validate prediction intervals (no streaming yet).
  2. Slice 2 (Telemetry Simulation): Build robust script generating realistic JSON telemetry (including sensor noise/dropouts).
  3. Slice 3 (Event Pipeline): Implement broker. Publish telemetry and successfully consume/acknowledge it reliably.
  4. Slice 4 (Anomaly Logic): Connect consumer to baseline bounds. Implement the persistence + threshold logic.
  5. Slice 5 (MLOps): Integrate experiment tracking to log drift, parameters, and alert frequency.
  6. Slice 6 (End-to-End): Containerization (Docker), API endpoints, and Final Integration Testing.

08 Testing & Evidence

Testing must cover both Data/ML correctness AND distributed/event-driven engineering.

Data & ML Correctness

  • Schema Validation: Strict Pydantic parsing of incoming telemetry JSON.
  • Data Leakage Prevention: Strict temporal train/test separation (no random shuffling of time-series).
  • Forecasting Metrics: MAE/RMSE evaluated on hold-out temporal sets.
  • Unit Tests: Mathematical correctness of derived features (e.g., VPD calculation).
  • Boundary Conditions: Handling of extreme but valid meteorological values.

Distributed Systems Engineering

  • Message Delivery: Handling malformed payloads and null data gracefully.
  • Idempotency & Offsets: Processing exact-once or at-least-once without duplicating alerts.
  • Temporal Integrity: Handling late or out-of-order messages relative to the forecast.
  • Broker Restart: Persistence of unacknowledged messages across broker crashes.
  • Consumer Disconnect: System recovers and processes backlog upon reconnection.
  • Sensor Dropout: Simulating edge hardware failure and resulting pipeline behavior.

11 Risks & Open Questions

Risk / Question Why It Matters How We Will Resolve It Status
Data Leakage Causes falsely high model accuracy, failing completely on the live stream. Strict temporal train/test splits. Never shuffle time-series data during validation. OPEN
Misleading Portfolio Claims Destroys credibility with senior technical reviewers. Explicitly label simulated data. Do not claim "enterprise scale" for local Docker deployments. OPEN
Poor / Noisy Data Garbage in, garbage out for the forecasting model. Conduct rigorous EDA before attempting to forecast. OPEN
Unrealistic Simulation If the edge data generator is too perfect, anomaly detection is trivial. Inject Gaussian noise and missing data spikes into the simulation script. OPEN
Overengineering Distracts from the core engineering demonstration. Strictly adhere to the "simplest architecture" rule. Reject tools without ADR evidence. OPEN
Arbitrary Thresholds Hardcoding 2σ without validating residual distribution invalidates scientific claims. Analyze residual distributions to define calibrated prediction intervals. OPEN

How to Use This Document From Day 1

Do not write pipeline or infrastructure code. Execute the following sequence:

  1. Locate the Data: Find a reliable historical dataset (e.g., Open-Meteo) and a corresponding soil moisture dataset (e.g., SMAP). Update the Scientific & Data Schema.
  2. Run EDA: Create a Jupyter notebook. Plot the variables over time. Look for correlations (e.g., VPD vs Moisture). Update Execution Log with findings.
  3. Clear Gate 1 & 2: Once EDA proves the data isn't just noise, change Gates 1 and 2 to VALIDATED.
  4. Build a Baseline: Train a simple statistical model (e.g., Persistence or ARIMA). Calculate RMSE. Define the prediction intervals. Update ADR-002.
  5. Clear Gate 3: If the baseline is mathematically defensible, change Gate 3 to VALIDATED.
  6. Begin Architecture Validation: Only now, write the simulated edge script and start testing Redis Streams vs alternatives (ADR-001).
The purpose of this document is not to predict the final architecture.
It is to create a disciplined process for discovering it.
